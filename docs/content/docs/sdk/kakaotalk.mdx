## KakaoTalkClient

The main client for interacting with KakaoTalk via the LOCO protocol. Unlike Discord/Slack which use stateless HTTP, KakaoTalk maintains a persistent TCP connection. Call `close()` when done.

```typescript
import { KakaoTalkClient } from 'agent-messenger/kakaotalk'

const client = await new KakaoTalkClient().login({ oauthToken, userId, deviceUuid })
// deviceUuid is optional — defaults to `agent-messenger-${userId}`
```

Or use automatic credential extraction — credentials are read from stored login state:

```typescript
import { KakaoTalkClient } from 'agent-messenger/kakaotalk'

const client = await new KakaoTalkClient().login()
```

### Login errors

The first operation opens the LOCO session lazily. If Kakao rejects `LOGINLIST`, `KakaoTalkError` preserves a typed code and safe numeric server status:

```typescript
import { KakaoTalkError } from 'agent-messenger/kakaotalk'

try {
  await client.getChats()
} catch (error) {
  if (error instanceof KakaoTalkError && error.code === 'invalid_access_token') {
    console.error(error.serverStatus) // -950
  }
}
```

- `invalid_access_token`: Kakao returned status `-950`; re-authenticate before retrying.
- `login_rejected`: Kakao returned another explicit authentication rejection.
- `login_failed`: booking, check-in, socket close, timeout, or another transport/protocol failure.

Rejected authentication closes the provisional session and never continues to `LCHATLIST` or sync-state work.

### Chat Rooms

```typescript
// List recent chat rooms (from login snapshot)
const chats = await client.getChats()
// → KakaoChat[]

// List ALL chats (paginate beyond login snapshot)
const allChats = await client.getChats({ all: true })

// Search chats by display name
const results = await client.getChats({ search: 'Alice' })

// Resolve user-set room titles via CHATINFO (one extra LOCO call per chat).
// Each KakaoChat gets a `title: string | null` matching the in-app room name.
// For open chats with no user-set title, the SDK falls back to the OpenLink
// link name via an additional INFOLINK call (only for OM / OD chats).
const titled = await client.getChats({ resolveTitles: true })

// Resolve a single chat's title directly (returns null on error or missing title).
// Open chats absent from the login snapshot use the link id from CHATINFO.
const title = await client.getChatTitle('9876543210')

// Fetch one complete KakaoChat directly via read-only CHATINFO.
// This also resolves rooms that are not present in the login-time chat list.
const chat = await client.getChat('9876543210')
```

### Messages

```typescript
// Get recent messages from a chat (default: 20)
const messages = await client.getMessages('9876543210')
// → KakaoMessage[]

// Get more messages
const more = await client.getMessages('9876543210', { count: 100 })

// Get messages after a known log ID
const newer = await client.getMessages('9876543210', { from: '123456789' })

// Reconcile history without dropping older messages when a protocol response
// contains more than `count`. Continue until `complete` is true.
let cursor: string | undefined = '123456789'
do {
  const page = await client.getMessagePage('9876543210', { from: cursor, count: 100 })
  await consume(page.messages)
  if (page.complete) break
  if (!page.next_cursor) throw new Error('KakaoTalk history made no cursor progress')
  cursor = page.next_cursor
} while (true)
```

Each `KakaoMessage` carries an `author_name: string | null`. The SDK auto-populates this from the same chat-list response that already arrives at login (no extra LOCO calls). It resolves for "display members" — the small set of nicknames KakaoTalk includes in the chat list — and is `null` for everyone else.

Each `KakaoMessage` also carries an `attachment: Record<string, unknown> | null`. For text messages this is `null`. For non-text messages (photos, videos, files, stickers, etc.) it is the parsed LOCO attachment payload — a JSON object whose shape varies by `type`. Photo messages use fields like `k` (CDN key), `w`/`h` (dimensions), `mt` (mime type), and `url`; sticker messages use `path`/`emoticonItemPath`. Treat it as opaque and narrow per `type`.

When a message tags users, `KakaoMessage` (and the listener's `KakaoTalkPushMessageEvent`) also carries `mentions?: KakaoMention[]`, lifted out of the attachment: `{ user_id: string, at: number[], len: number }`. `user_id` is an exact decimal string (open-chat ids exceed 2^53), `at` lists the 1-based ordinals of the `@` characters in `message` that start the tag, and `len` is the tagged name's length without the `@`. The key is absent when there are no mentions.

`KakaoMessage` and the listener's `KakaoTalkPushMessageEvent` also expose three optional raw chat-log fields. Each is present only when the server sent it, so existing consumers see no change for messages without them:

- `scope?: number` — the chat-log scope. Observed: `1` for ordinary messages, `3` for open-chat thread replies.
- `thread_id?: string` — the chat-log thread id as an exact decimal string (omitted when absent or zero). Observed to equal the parent message's `log_id` for thread replies. It is read from the top-level `threadId` and, when that is missing, from the chat log's `supplement` JSON.
- `prev_id?: string` — the chat-log previous log id as an exact decimal string (omitted when absent or zero).

The SDK passes these through without interpreting them. The scope/thread mapping above is observed behavior, not a documented protocol contract. Thread replies are a different feature from quoted replies (`type: 26`, which carry `attachment.src_logId`).

```typescript
const messages = await client.getMessages('9876543210', { count: 100 })
const threadReplies = messages.filter((m) => m.scope === 3 && m.thread_id !== undefined)
```

### Members

```typescript
// List all members through the compatibility array API
const members = await client.getMembers('9876543210')
// → KakaoMember[]

// Read the exact snapshot contract and its consistency evidence
const snapshot = await client.getMemberSnapshot('9876543210')
// → KakaoMemberSnapshot {
//     chat_id, active_members, members, complete: true,
//     consistency_basis: 'stable_double_read_chatinfo_getmem'
//   }

// Resolve a specific subset by user_id (LOCO MEMBER) — useful for >100-member rooms
const subset = await client.getMembersByIds('9876543210', ['1234567890', '9876543210'])
```

`getMemberSnapshot()` compares two read-only `CHATINFO` observations
and two complete `GETMEM` observations. It succeeds only when the active
count, display-member subset, and full member-ID set are stable. It does
not call `CHATONROOM`, so it does not enter the room or advance unread
state. Any malformed, partial, or changing snapshot fails closed.

Each `KakaoMember` includes `user_id`, `nickname`, profile image URLs, `status_message`, `country_iso`, `user_type` (nullable; `null` when the server omits the field), and open-chat-only fields (`open_token`, `open_profile_link_id`, `open_permission` — the last is the OpenChannelUserPerm bitfield: `1`=OWNER, `2`=NONE, `4`=MANAGER, `8`=BOT).

### Read Status

```typescript
import { KakaoTalkClient, computeReadStatus } from 'agent-messenger/kakaotalk'

// Seed: the last log ID each member has read in the chat
const watermarks = await client.getReadWatermarks('9876543210')
// → KakaoReadWatermarks {
//     chat_id: '9876543210',
//     watermarks: [
//       { user_id: '1234567890', watermark: '3846830417126748160' },
//       { user_id: '2345678901', watermark: '3846830417126000000' },
//     ],
//   }

// Who has read a specific message
const status = computeReadStatus(watermarks, '3846830417126748160', {
  senderId: '1234567890', // the message's author — never counted
})
// → KakaoReadStatus {
//     chat_id: '9876543210',
//     log_id: '3846830417126748160',
//     unread_count: 1,
//     read_by: [],
//     unread_by: ['2345678901'],
//   }
```

A member has read the message once their watermark is at or past its log ID (`watermark >= log_id`, compared exactly as 64-bit integers). Pass the message's sender as `senderId` (and optionally `excludeUserIds`, e.g. yourself) — excluded members are never counted, so `unread_count` matches the number KakaoTalk shows next to the message.

`getReadWatermarks` sends CHATONROOM, the room-entry command: the server may clear your own unread count for that chat (see #315), so call it on demand — never from passive polling. It is also a seed-once call: the server includes the `a` (member ids) / `w` (watermarks) arrays only on the first CHATONROOM for a chat within a LOCO session, so a repeat call throws `KakaoTalkError('get_read_watermarks_failed')`. Seed once per session, then advance watermarks from `KakaoTalkListener` `read` events (DECUNREAD pushes; a watermark only moves forward). When the listener emits `disconnected`, drop the seed so the next call re-seeds in the new session. For a side-effect-free live feed, rely on `read` events instead of polling CHATONROOM.

### Sending

```typescript
// Send a text message
const result = await client.sendMessage('9876543210', 'Hello from SDK!')
// → KakaoSendResult { success, status_code, chat_id, log_id, sent_at }
```

```typescript
// Mention members — the text must contain @<name> for each one
await client.sendMessage('9876543210', '@Alice @Bob standup in 5', {
  mentions: [
    { user_id: '1234567890', name: 'Alice' },
    { user_id: '2345678901', name: 'Bob' },
  ],
})

// Mentions combine with quoted replies (not yet verified against a live server)
const recent = await client.getMessages('9876543210', { count: 100 })
const replyTo = recent.find((m) => m.log_id === '123456789')! // KakaoMessage satisfies KakaoReplyTarget
await client.sendMessage('9876543210', '@Alice agreed', {
  replyTo,
  mentions: [{ user_id: '1234567890', name: 'Alice' }],
})
```

`mentions` takes `KakaoMentionInput[]` (`{ user_id, name }`). The SDK finds each `@<name>` in the text, computes the `at`/`len` that KakaoTalk expects, and writes `user_id` as an exact 64-bit integer into the WRITE `extra`. If a name is not found in the text, or two different users share the same name, `sendMessage` throws `KakaoTalkError('invalid_mention')` before anything is sent. When names share a prefix (`@Kim` vs `@Kimberly`), each `@` goes to the longest matching name, and a name ending in a Latin letter or digit only matches when the next character is not another one (`@Kimberly` alone does not tag `Kim`). To tag by id only, resolve the nickname first, e.g. with `getMembersByIds(chatId, [userId])`. `len` counts code points; that is verified for Hangul and Latin names, but not yet for names with characters outside the BMP (such as emoji). Mentions inside a quoted reply (`replyTo`, a `KakaoReplyTarget`; a `KakaoMessage` from `getMessages` fits it) are built the same way but have not yet been verified against a live server.

`sendMessage` also accepts boolean `silence` and `noSeen` options. Omit them to keep the defaults (`false`). Shared WRITE headers preserve the existing mention, quoted-reply, and attachment `extra` data. Client message IDs are generated per device and retained across reconnects; they are not durable job IDs and do not provide cross-process deduplication.

`success` requires successful packet and body statuses and a valid positive `log_id`. Body rejections are returned in `status_code` even if the outer packet status is zero. An acknowledgment with `status_code: 0` and `log_id: '0'` created no message, so it is reported as `success: false`. Quoted replies (`sendMessage(chatId, text, { replyTo })`) in open chats get the room's `src_linkId` automatically, from the login snapshot or, when the room is missing there, from a read-only `CHATINFO` lookup. Pass `replyTo.link_id` (a decimal string) to supply the link id yourself and skip that lookup; a value that is not a positive signed 64-bit decimal is rejected with `invalid_link_id` before anything is sent.

```typescript
// Reply to a message you already received, e.g. from the listener
await client.sendMessage(chatId, 'Got it', {
  replyTo: { log_id: event.log_id, author_id: event.author_id, message: event.message, type: event.message_type },
})
```

#### Attachments

`sendAttachment` is the single entry point for outbound photos, videos, audio, files, and multi-photo galleries. It accepts either one buffer or an array of `{ data, filename, mime? }` tuples; MIME is sniffed from the filename when not given, and the client dispatches to the right LOCO message_type internally.

```typescript
// Single attachment — MIME inferred from the filename extension
//   image/* → photo, video/* → video, audio/* → audio, anything else → file
await client.sendAttachment('9876543210', photoBytes, 'cat.jpg')
await client.sendAttachment('9876543210', pdfBytes, 'report.pdf')

// Force a specific MIME (extension-less files, or to send a video as a generic file)
await client.sendAttachment('9876543210', mp4Bytes, 'clip.mp4', 'application/octet-stream')

// Multiple attachments — the client picks the right wire flow:
//   all-image (length >= 2) → multi-photo gallery (sendMultiPhoto under the hood)
//   mixed kinds              → sequential individual sends, fail-fast on first error
//   length === 1             → equivalent to the single-buffer overload
await client.sendAttachment('9876543210', [
  { data: photo1, filename: 'a.jpg' },
  { data: photo2, filename: 'b.png' },
  { data: photo3, filename: 'c.webp' },
])

await client.sendAttachment('9876543210', [
  { data: photo, filename: 'screenshot.png' },
  { data: spec, filename: 'spec.pdf' },
])
// → KakaoSendResult of the last successful send (or the first failure, if any)
```

The typed helpers `sendPhoto`, `sendVideo`, `sendAudio`, `sendFile`, and `sendMultiPhoto` remain available when you want to bypass MIME sniffing and dispatch to a specific message_type explicitly.

### Leave Chat

```typescript
const result = await client.leaveChat('9876543210')
// → { success: true, status_code: 0, chat_id: '9876543210' }
```

Leaves a chat room by its chat ID. Works on 1:1, group, open, and PlusChat rooms. Returns `success: true` on a successful leave. The departed chat is immediately evicted from the client's cached chat list — a subsequent `getChats()` call will not include it.

### Open Chat Moderation

```typescript
// Kick a member (irreversible; also blocks them from rejoining via the link)
const kicked = await client.kickMember('9876543210', '1234567890')
// → KakaoKickMemberResult { success: true, status_code: 0, chat_id: '9876543210', user_id: '1234567890' }

// List members on the kick list
const kickList = await client.getKickList('9876543210')
// → KakaoKickList { success: true, status_code: 0, chat_id: '9876543210', members: KakaoKickedMember[] }

// Remove a member from the kick list so they can rejoin (does not re-add them)
const unkicked = await client.unkickMember('9876543210', '1234567890')
// → KakaoUnkickMemberResult { success: true, status_code: 0, chat_id: '9876543210', user_id: '1234567890' }
```

Open chats only; the account must be the room's host or a co-host. The open chat link ID is resolved from the chat ID (login snapshot first, then read-only `CHATINFO`), so callers pass only the chat ID. `kickMember` performs no confirmation of its own — gate it in your application.

Each `KakaoKickedMember` has `user_id`, plus `nickname`, `chat_id`, and `kicked_at`, which are `null` when the server omits them.

Errors:

- Regular (non-open) chats throw `KakaoTalkError('not_open_chat')` before any moderation packet is sent.
- Server rejections (for example, missing host or co-host permission) do not throw: they return `success: false` with the server's non-zero `status_code`. `getKickList` returns an empty `members` array in that case.
- A successful `KLSYNC` response without a `kickMembers` array throws `get_kick_list_failed` instead of returning an empty list. Only `kickMember` (`KICKMEM`) has been used against a live server; the `KLSYNC` and `KLDELITEM` request shapes and the kick-list response fields are unverified.
- Transport failures, including the synthetic `-1` LocoConnection emits on disconnect, throw `kick_member_failed` / `get_kick_list_failed` / `unkick_member_failed` so `executeWithReconnect` can retry on a fresh session.
- Non-numeric `chatId` / `userId` throw `invalid_chat_id` / `invalid_user_id`.

### Typing Indicator

```typescript
// Fire a single typing pulse — the recipient sees the animated "…" dots
const result = await client.sendTyping('9876543210')
// → KakaoTypingResult { success: true, status_code: 0, chat_id: '9876543210' }

// For OpenChat rooms, pass the linkId
await client.sendTyping('9876543210', { linkId: '77777' })
```

The KakaoTalk client-side lifetime is ~5s per pulse — to keep the indicator visible while generating a long reply, re-fire faster than that (e.g. every 3s):

```typescript
const interval = setInterval(() => {
  client.sendTyping('9876543210').catch(() => {}) // ignore transient errors
}, 3000)

try {
  const reply = await generateReply()
  await client.sendMessage('9876543210', reply)
} finally {
  clearInterval(interval)
}
```

Errors follow the same shape as `markRead`: transport-level failures (non-zero `statusCode`, including the synthetic `-1` LocoConnection emits on disconnect) throw `KakaoTalkError('send_typing_failed')` so `executeWithReconnect` can retry on a fresh session. Non-numeric `chatId` / `linkId` throw `invalid_chat_id` / `invalid_link_id`.

### Cleanup

```typescript
// Close the LOCO connection (MUST call when done)
client.close()
```

Once closed, any subsequent method call throws a `KakaoTalkError` with code `client_closed`. Create a new client if you need to reconnect.

## OAuth Token Refresh

`refreshKakaoOAuthToken()` explicitly exchanges a stored Android sub-device refresh token for a new token set. It is stateless and caller-invoked: it does not update credential files, retry `LOGINLIST`, or run automatically after an authentication failure.

```typescript
import { refreshKakaoOAuthToken } from 'agent-messenger/kakaotalk'

if (!account.refresh_token) throw new Error('No KakaoTalk refresh token')

const refreshed = await refreshKakaoOAuthToken(
  {
    accessToken: account.oauth_token,
    refreshToken: account.refresh_token,
    deviceUuid: account.device_uuid,
  },
  { timeoutMs: 15_000 },
)

const nextAccount = {
  ...account,
  oauth_token: refreshed.accessToken,
  refresh_token: refreshed.refreshToken,
  updated_at: new Date().toISOString(),
}

await persistAccountAtomically(nextAccount) // Application-defined durable storage
```

The result always includes both tokens. Kakao may rotate the refresh token, so persist the entire returned token set atomically before the process exits or another client uses the credential. Never refresh a copied production credential and discard the result.

Failures throw `KakaoOAuthRefreshError` with a safe `code` and optional `serverStatus` or `httpStatus`; token values and raw response bodies are not retained. This uses an undocumented Android endpoint and may change without notice.

## KakaoTalkListener

Real-time event listener that receives push events from KakaoTalk via the LOCO protocol. Subscribes to the underlying client's LOCO session.

```typescript
import { KakaoTalkClient, KakaoTalkListener } from 'agent-messenger/kakaotalk'

const client = await new KakaoTalkClient().login()
const listener = new KakaoTalkListener(client)

listener.on('connected', (info) => {
  console.log(`Connected as ${info.userId}`)
})

listener.on('message', (event) => {
  console.log(`[${event.chat_id}] ${event.author_id}: ${event.message}`)
})

listener.on('member_joined', (event) => {
  console.log(`User ${event.member.user_id} joined ${event.chat_id}`)
})

listener.on('member_left', (event) => {
  console.log(`User ${event.member.user_id} left ${event.chat_id}`)
})

listener.on('read', (event) => {
  console.log(`User ${event.user_id} read ${event.chat_id} up to ${event.watermark}`)
})

listener.on('disconnected', () => console.log('LOCO session dropped'))
listener.on('error', (err) => console.error(err))

await listener.start()
// listener.stop() to disconnect
```

### Events

| Event             | Payload                     | Description                             |
| ----------------- | --------------------------- | --------------------------------------- |
| `message`         | `KakaoTalkPushMessageEvent` | New message received                    |
| `member_joined`   | `KakaoTalkPushMemberEvent`  | Member joined a chat                    |
| `member_left`     | `KakaoTalkPushMemberEvent`  | Member left a chat                      |
| `read`            | `KakaoTalkPushReadEvent`    | Read receipt (unread count decreased)   |
| `kakaotalk_event` | `KakaoTalkPushGenericEvent` | Catch-all for all push events           |
| `connected`       | `{ userId: string }`        | Connected to LOCO server                |
| `disconnected`    | —                           | LOCO session dropped (see Reconnection) |
| `error`           | `Error`                     | Connection or protocol error            |

### Reconnection

The listener does not implement a reconnection loop. Behavior on session drop:

- **Server-requested migration (`CHANGESVR`)** — The client invalidates the session, emits `disconnected`, and immediately establishes a new session in the background. Subscribers receive `connected` again once it succeeds. No action required.
- **Network drop or peer close** — The client emits `disconnected` and clears its session state. The next SDK API call (`getChats`, `getMessages`, `sendMessage`) will lazily re-establish the session via `executeWithReconnect`. The listener itself stays passive — to resume push delivery after a drop, call `await client.acquireSession()` (or any API call) from your `disconnected` handler.
- **Kicked by another device (`KICKOUT`)** — The listener stops and emits `error`. This is terminal; you must `login()` a new client to recover.

If you need a long-running listener that survives network drops, wrap `acquireSession()` in your own retry loop driven by the `disconnected` event.

## KakaoCredentialManager

Manages KakaoTalk credentials stored at `~/.config/agent-messenger/kakaotalk-credentials.json`. Files are written with `0o600` permissions.

```typescript
import { KakaoCredentialManager } from 'agent-messenger/kakaotalk'

const manager = new KakaoCredentialManager()
```

```typescript
// Load full config from disk (returns defaults if file doesn't exist)
const config = await manager.load()
// → KakaoConfig { current_account, accounts }

// Save full config to disk
await manager.save(config)

// Get the current account's credentials
const account = await manager.getAccount()
// → KakaoAccountCredentials | null

// Get a specific account by ID
const specific = await manager.getAccount('1234567890')
// → KakaoAccountCredentials | null

// Store account credentials
await manager.setAccount(credentials)

// Remove an account
await manager.removeAccount('1234567890')

// Switch the current account
await manager.setCurrentAccount('1234567890')
```

## Examples

### Chat Summary

List all chats, count unread, and print a summary.

```typescript
import { KakaoTalkClient, KakaoCredentialManager } from 'agent-messenger/kakaotalk'

const manager = new KakaoCredentialManager()
const account = await manager.getAccount()
if (!account) throw new Error('Not authenticated')

const client = await new KakaoTalkClient().login({
  oauthToken: account.oauth_token,
  userId: account.user_id,
  deviceUuid: account.device_uuid,
})

try {
  const chats = await client.getChats({ all: true })
  const unread = chats.filter((c) => c.unread_count > 0)
  console.log(`${unread.length} chats with unread messages:`)
  for (const chat of unread) {
    console.log(`  ${chat.display_name} — ${chat.unread_count} unread`)
  }
} finally {
  client.close()
}
```

```typescript
import { KakaoTalkClient, KakaoCredentialManager } from 'agent-messenger/kakaotalk'

}
```

### Message Monitor

Poll for new messages in a chat room.

```typescript
import { KakaoTalkClient, KakaoCredentialManager } from 'agent-messenger/kakaotalk'

const manager = new KakaoCredentialManager()
const account = await manager.getAccount()
if (!account) throw new Error('Not authenticated')

const client = await new KakaoTalkClient().login({
  oauthToken: account.oauth_token,
  userId: account.user_id,
  deviceUuid: account.device_uuid,
})
const chatId = '9876543210'

let lastLogId: string | undefined

const poll = async () => {
  try {
    const messages = lastLogId
      ? await client.getMessages(chatId, { from: lastLogId })
      : await client.getMessages(chatId, { count: 1 })

    for (const msg of messages) {
      if (msg.log_id !== lastLogId) {
        console.log(`[${msg.author_id}] ${msg.message}`)
        lastLogId = msg.log_id
      }
    }
  } catch (error) {
    console.error('Poll failed:', error)
  }
}

const timer = setInterval(poll, 10_000)

// To stop: clearInterval(timer); client.close()
```

### Transport and interrupted sends

On the measured Linux Node 24.14.1 / OpenSSL 3.5.5 and macOS arm64 Node 26.13.0 / OpenSSL 4.1.0 builds, tablet messaging selects a calibrated 228-byte ClientHello offer by default: nine AEAD cipher suites, OCSP status request, retained SNI, and respectively three/four signature schemes. Other platform/runtime combinations retain the previous broader offer. This is an exact-build calibration, not an assertion about all Node versions or an official-client fingerprint. Certificate verification remains enabled.

The narrower signature lists can limit compatibility with future server certificates. An OCSP request is not itself OCSP validation; the tested server returned no stapled response. A 228-byte total does not make the internal offer identical to Android or prevent server-side differentiation. Revalidate the profile after runtime/server changes, including authenticated login; do not extend the runtime match merely to force a byte count.

Android tablet messaging uses certificate-verified TLS on port 10009, preferring AES-128-GCM and X25519. The TLS service identity is `kakao.com`, used for both SNI and certificate hostname verification; it is distinct from the booking-provided routing host/IP. Existing desktop, booking, checkin, and media-upload transports are retained. Matching the negotiated cipher does not make this an official client or establish identical TLS handshakes.

Read operations can reconnect and retry after a disconnect. By default, text/reply and media sends are not automatically replayed after an uncertain failure. A `delivery_unknown` error means the server may already have accepted the request: a retry may deliver a duplicate. Inspect history before manually retrying. A send that was written but not acknowledged before the packet timeout, and a media upload whose completion notice never arrives, are also reported as `delivery_unknown`. Other errors can still leave acceptance uncertain; absence of `delivery_unknown` is not a safe retry signal.

Explicit opt-in retries an uncertain send once, reconnecting if the main session was lost:

```typescript
const client = new KakaoTalkClient({ retryUnknownDelivery: true })
await client.login()
// Applies to this client's text/reply and media sends; duplicates are possible.
await client.sendMessage(chatId, text)
```

The CLI equivalent is `message send ... --retry-unknown-delivery` or `message upload ... --retry-unknown-delivery`. The opt-in does not retry every server rejection or generic error, and repeated media operations can repeat uploads. Known provider rejections need their own verified transient/non-acceptance policy. This is not an exactly-once or cross-process deduplication guarantee.

New Android device identifiers generated during auth registration use the observed salted SHA-256 UUID/time derivation. Previously registered device identifiers are reused unchanged. Direct SDK `login()` without `deviceUuid` retains its `agent-messenger-${userId}` fallback; pass the registered identifier explicitly. Login keeps the existing role-specific identity/version (tablet on the tablet role and PC on the PC role), defaults `isSw` to `false` on the tablet role (configurable/omittable; the PC role omits it unless set), and defaults to zero block-list revisions in `rp`; it does not copy another device's private settings.

Client message IDs normalize the device suffix to 0–99 and retain an unwrapped counter across time/integer boundaries. This deliberately avoids negative IDs and immediate wrap collisions; the finite ID space and process-local generator are not a durable deduplication mechanism.

### Protocol fields: meaning, defaults, and evidence limits

The transport flow has three different requests: **GETCONF (booking)** discovers routing endpoints, **CHECKIN** supplies the user/device/network context and returns the messaging host/port, and **LOGINLIST** authenticates that messaging connection and exchanges synchronization state. CHECKIN is not a room check-in, message send, or proof of login completion. A field seen in one stage is not automatically required in another.

This baseline uses Android 26.9.2 request builders and preserved Kotlin metadata, with searches across all 39 DEX files. Static references were traced to the relevant request writers and callers; this is not exhaustive dynamic coverage of every feature/server/account. The official TLS application payload was not decrypted. The table distinguishes observed behavior from SDK policy.

The WRITE header defaults (`msgId`, `scope`, `silence`, empty `extra`) and the `isSw` default apply to the tablet role, where they were verified live. On the PC role, a WRITE keeps the earlier SDK shape unless WRITE options are passed, and LOGINLIST omits `isSw` unless `isSwitching` is set.

#### Which account switch does `isSw` describe?

The preserved supplier name is `isAccountSwitching`, but the located Android setup callers both supply constant-false providers. No true-producing setup caller was found in this APK. The tablet/PC role is separately represented by `dtype`, `useSub`, and `os`; selecting that role is not evidence for setting `isSw=true`. No connection from multi-profile selection or a desktop multi-account UI to this supplier was established. Account-switch strings elsewhere in the APK include KakaoPay flows and must not be treated as evidence for this LOCO flag without a call/data-flow link.

Consequently, this baseline does not identify an enabled product workflow for true. `isSwitching` is an advanced wire override, not an SDK account-switch API, and must not be enabled merely when changing display profiles, using a tablet, or choosing another stored SDK account. Establish the relevant account/authentication transition before using true. The false/omission login tests do not validate such a transition.

#### Why not load block revisions from an existing database?

The official app does load its own revisions from local storage: Android DataStore (`blockRevision`, `plusBlockRevision`), with migration paths from preferences. The SDK's current `SyncState` stores chat-list synchronization fields, not block-list contents/revisions, and has no implemented block-list synchronization lifecycle. Its chat `revision` is a different field and must not be substituted for either block revision.

The SDK therefore has no authoritative local block snapshot from which to infer nonzero values. Zero describes the missing-state baseline; advanced callers with a matching block-state implementation can supply their saved snapshot instead of being forced to zero. These are session inputs, not values a caller should invent for each request. Future SDK block-list synchronization should persist and load its account/device-scoped revisions automatically together with the corresponding lists. Reading another app's private storage, or only copying its revision while omitting its list state, is not an equivalent implementation.

#### What the compatibility tests establish

All four combinations of `isSw` omitted/false and `countryISO` KR/omitted passed real tablet-role login and PING on the same existing account/identity, with zero messages sent. This establishes acceptance for that tested environment, not universal equivalence or a requirement to change the earlier fields. `isSwitching: true`, non-KR routing, nonzero block revisions, and thread visibility are not live-certified by that matrix.

These field choices are a configurable compatibility baseline, not evidence that the earlier SDK could not work otherwise. Reliability behavior (acknowledgement validation and uncertain-send policy) has separate evidence. Default alignment alone does not establish a required bug fix.
